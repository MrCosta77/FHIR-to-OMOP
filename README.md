# Clinical Mapping Framework: FHIR to OMOP CDM

This repository contains a local, privacy-first data engineering pipeline that transforms raw synthetic clinical data (FHIR) into the OMOP Common Data Model (CDM). 

I built this project to focus on a real-world challenge in Health Data Science and Real-World Evidence (RWE): handling messy, unstructured clinical text that fails standard deterministic ETL mapping.

## Overview

The core of this pipeline is built with Python and DuckDB to process patient data generated by Synthea. While standard OMOP mapping covers the clean data, I implemented an AI-assisted fallback module using a local LLM (Qwen2.5-coder) to semantically normalize unmapped terms without ever sending data to an external API.

The project is structured in two phases: an exploratory phase using Jupyter Notebooks, and a production-oriented phase utilizing modular Python scripts and automated data quality testing.

## Architecture & Tech Stack

*   **Data Generation:** Synthea (FHIR JSON Bundles)
*   **Database / SQL Engine:** DuckDB (Chosen for in-process, memory-efficient analytical queries over the 6.4M+ OMOP vocabulary concepts)
*   **Orchestration:** Python 3.12 (Jupyter Notebooks & Modular Scripts)
*   **Testing:** Pytest (Data quality & referential integrity)
*   **AI Engine:** Local Ollama instance running `qwen2.5-coder:7b`

## Core Engineering Decisions

During development, I prioritized data integrity, clinical rigor, and privacy over complex features:

1.  **Deterministic Relational Integrity:** Instead of relying on non-deterministic functions, I used cryptographic hashing (`hashlib.sha256`) on the original FHIR UUIDs. This ensures the `person_id` remains stable across different ETL runs, keeping the bridge between clinical tables intact.
2.  **Idempotency:** The pipeline is designed to be re-run safely. Staging and target tables use `ON CONFLICT` updates or are cleared prior to insertion to prevent record duplication.
3.  **Strict Privacy (Local-Only):** By running the LLM locally via Ollama, the architecture guarantees that zero clinical data (simulated or real) leaves the machine.
4.  **Automated Data Quality:** Implemented Pytest fixtures to enforce relational integrity (preventing orphan records) and validate temporal logic (e.g., no future dates in clinical events).
5.  **Controlled Chaos Injection (RWE Simulation):** To prove the AI fallback's utility, the laboratory ETL intentionally strips the clean LOINC codes from 20% of the FHIR observations, simulating the noisy, unstructured data typical of legacy Hospital Information Systems (HIS).

## Project Structure

### Phase 1: Exploratory ETL (Jupyter Notebooks)
*   `01` to `03`: Generates synthetic population, loads Athena vocabularies, and extracts demographics (`PERSON`).
*   `04` to `06`: Processes diagnoses (`CONDITION_OCCURRENCE`) and introduces the AI semantic fallback loop (Jaro-Winkler similarity).
*   `07` to `08`: Extracts prescriptions (`DRUG_EXPOSURE`), resolving complex HL7 FHIR cross-references to standard RxNorm concepts.
*   `99_data_detective.ipynb`: A diagnostic notebook used to investigate missing raw FHIR data and map ETL failures.

### Phase 2: Modular Engineering & Laboratory Data (`src/` & `tests/`)
*   `src/etl/measurement.py`: Extracts quantitative lab results and vital signs. Injects "chaos" to simulate legacy data.
*   `src/mapping/llm_measurement.py`: The AI semantic pipeline targeting the LOINC vocabulary.
*   `src/utils/`: Centralized configurations and hashing helpers.
*   `tests/test_data_quality.py`: Automated Pytest suite validating the OMOP schema integrity.

## Case Study: The LOINC Challenge & Architectural Limits

During the implementation of the `MEASUREMENT` table (Phase 2), a critical architectural limitation was documented regarding text-based heuristics in clinical biochemistry. 

While Jaro-Winkler and SQL Substring (`LIKE`) matching worked reasonably well for diagnoses (SNOMED), it failed against the structural complexity of **LOINC** (which utilizes 6 distinct classification axes). The purely orthographic matching resulted in critical clinical false positives:
*   **Sample Axis Loss:** Blood tests were mapped to stool or stone samples simply because the analyte name matched.
*   **Immunological Context Loss:** Allergen-specific tests (e.g., *Peanut IgE Ab*) were stripped of their allergen by the LLM, leading the SQL engine to map it to random allergens (e.g., *Yam IgE Ab*).
*   **Biomarker vs. Formula:** Complex calculations (like eGFR) were incorrectly reduced to the underlying molecule (Creatinine).

**Conclusion:** Complex clinical vocabularies cannot be safely mapped using free-text heuristics.

## Known Limitations & Next Steps (v2.0)

*   **Vector Embeddings & RAG:** The current AI fallback relies on string similarity and substring matching to validate the LLM's output against the OMOP dictionary. Based on the LOINC audit above, a future iteration will replace this module with a robust **Semantic Search** architecture. This will involve converting the OMOP dictionary into Vector Embeddings and using a Retrieval-Augmented Generation (RAG) pipeline to anchor the LLM's decisions in true clinical context (Cosine Similarity) rather than orthographic overlap.
*   **Unit Conversion (UCUM):** Implementing standard unit conversion logic for quantitative measurements.

## Setup

1. Clone the repository and set up a virtual environment.
2. Install dependencies: `pip install -r requirements.txt`
3. Download the OMOP vocabularies from Athena and place them in the appropriate data folder.
4. Run the data quality tests: `pytest -v`
5. Note: You must have [Ollama](https://ollama.com/) installed and running locally with the `qwen2.5-coder:7b` model pulled to execute the AI mapping modules.
